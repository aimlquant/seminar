# seminar-deck-v1 디자인 규칙

이 템플릿은 `study` 저장소의 `study-deck-v1` 을 세미나용으로 파생한 1280×720 HTML 덱이다.
정보 위계, 발표 UX, 시각 컴포넌트, 자동 목차, 추적 계약은 그대로 승계하고 **교재 전제만 출처
전제로 바꿨다.** 로고·고객명·개인 브랜딩은 포함하지 않는다.

- 완성 기준 예시: `html/seminars/computer-use/index.html`
- 공통 설계 청사진: `agent-support/templates/SEMINAR_SESSION_BLUEPRINT.md`

한 세미나의 기본 산출물은 `seminar-report-v1` 상세 리포트와 이 발표자료의 쌍이다. 1차 자료에서
리포트를 먼저 완성·검증하고 이 덱은 그 리포트에서만 파생한다. 리포트는 사후 학습을 위한 맥락과
근거를 보존하고, 슬라이드는 같은 주장·용어·표·도형을 발표 흐름과 핵심 메시지로 압축한다.
**슬라이드에만 존재하는 새 주장을 만들지 않는다.**

## 스터디와 다른 점

세미나는 보존해야 할 원본 목차가 없다. 발표자가 구성한 섹션이 곧 원본이고, 근거는 벤더 공식
문서·표준 문서·직접 측정 같은 1차 자료다. 따라서 다음이 달라진다.

| study-deck-v1 | seminar-deck-v1 |
|---|---|
| `source_fidelity` · 원본 장·절 번호·제목 순서 보존 | 없음. 발표자가 구성한 섹션 순서가 정본 |
| `data-source-refs="section:3.1 figure:3.2"` | `data-source-refs="vendor:anthropic-computer-use ref:1"` |
| 화면에 `교재 §3.2.2`, `Listing 3.7` 좌표 표시 | 화면에 1차 자료 이름과 확인일 표시 |
| `study_id` · `chapters` | `seminar_id` · `sections` |
| 50분 18\~30장 | 60분 40\~50장까지 허용 |

`data-report-refs` 추적 계약, 자동 목차, 리포트 게이트는 **바뀌지 않는다.** 그것이 이 형식의
본체다.

## 출처 계약

세미나의 근거는 교재 좌표가 아니라 1차 자료다. 다음 형식으로 기록한다.

- `data-source-refs` 토큰: `vendor:<슬러그>` · `spec:<슬러그>` · `measured:<날짜>` · `ref:<번호>`
- `ref:<번호>` 는 리포트 참고문헌의 항목 번호를 가리킨다
- 화면에는 `.source-note` 로 자료 이름과 **확인일** 을 함께 표시한다
- 벤더 문서와 표준 문서는 버전·개정일이 바뀌므로 확인일 없는 인용을 남기지 않는다
- 직접 측정한 수치는 `measured:` 로 표시하고 측정 조건을 근접 출처에 적는다

## 표준 발표 흐름

60분 발표 기준 40\~50장을 권장한다. 세미나는 시리즈 없이 한 번에 완결되므로 스터디보다 도입과
마무리에 무게를 더 둔다.

1. 표지
2. 훅 — 청중이 방금 본 것 또는 방금 겪은 문제
3. 오늘의 여정 — 섹션 지도
4. 섹션 구분
5. 정의와 경계
6. 왜 지금인가
7. 구성요소와 관계
8. 섹션 구분
9. 대안 지형 비교
10. 각 대안의 강점과 한계
11. 섹션 구분
12. 실제로 해보면 어떻게 되는가
13. 관측된 결과와 조건
14. 섹션 구분
15. 실패 양상과 위험
16. 통제 수단
17. 도입 판단 기준
18. 확인 질문
19. 세 문장 요약과 Q&A

내용에 맞지 않는 장은 합치거나 제거할 수 있다. 첫 3장과 마지막 2장 사이의 본문은 리포트의 섹션
순서를 따른다. `정의 → 지형 → 실증 → 위험 → 판단` 은 내용 점검에 사용하고 리포트 목차를
대체하지 않는다.

## 핵심 원칙

- 배경은 따뜻한 회백색, 액센트는 진청 한 색을 기본으로 사용한다.
- 한 슬라이드에는 하나의 메시지만 두고 제목, 한 줄 설명, 본문, takeaway 순서로 읽히게 한다.
- 한 슬라이드에는 의미 있는 그림 하나만 두는 것을 기본으로 한다. 서로 다른 그림의 동시 비교가
  학습 과제이고 두 그림이 최종 크기에서 모두 읽힐 때만 한 장에 함께 둔다.
- 제목은 사실 이름보다 결론형 문장으로 쓴다. `기술 A의 특징` 보다 `기술 A는 검증 비용을 줄인다`
  가 낫다.
- 단, 섹션 구분 슬라이드와 각 섹션의 첫 슬라이드는 리포트 섹션 제목을 주 제목으로 사용한다.
- 결론형 제목 가까이에 1차 자료 이름과 확인일을 간결하게 표시한다.
- 기본 글자 크기를 줄여 내용을 밀어 넣지 않는다. 내용이 넘치면 슬라이드를 나눈다.
- 섹션 구분 제목은 `.section-copy` 안에 두고 길이에 따라 명시적으로 밀도를 선택한다.
- 같은 의미 층위의 4개 카드는 `.card-grid--four` 로 공통 열 너비·상하선을 맞춘다.
- 외부 폰트, CDN, 프레임워크 없이 세미나 폴더만으로 동작해야 한다.
- 템플릿 CSS와 JavaScript는 세미나 폴더에 복사한다. 과거 세미나에 일괄 덮어쓰지 않는다.

## 제공 컴포넌트

`study-deck-v1` 의 컴포넌트를 그대로 승계한다.

- `.slide--cover`, `.slide--section`, `.slide--closing`: 표지·섹션 구분·마무리
- `.section-copy`, `.slide--section[data-density="long"]`: 짧고 긴 섹션 제목의 위계
- `.two-col`, `.panel`: 문제/해법, 이전/이후, 두 대안 설명
- `.card-grid`, `.card`, `.card-grid--four`: 세 역할·가치·요점, 네 카드 공통 그리드
- `.kpi-grid`, `.kpi`: 수치 또는 검증 가능한 근거
- `.flow`, `.access-path`, `.shift`, `.maturity-line`: 순서·책임 경로·전환·성숙 단계
- `.graph-scene`, `.graph-node`, `.graph-edge`, `.legend-row`: 개체와 관계의 개념도
- `.balance-grid`: 강점과 한계
- `.hybrid-loop`: 검증·피드백 운영 루프
- `.pillar-grid`: 네 설계 원칙
- `.use-case-grid`, `.conversation`: 사례의 역할 분담과 대화 흐름
- `.decision-grid`: 적합·비적합 신호
- `.compare-table`, `.compare-table--dense`, `.semantic-grid`: 반복 필드 비교와 의미 구조
- `.question-list`: 발표 확인 질문
- `.code-block`, `.code-layout`: 핵심 코드·데모
- `.takeaway`, `.source-note`: 핵심 문장과 근접 출처
- `.slide--visual`, `.report-visual-body`, `.deck-report-figure`: 리포트 그림의 발표 크기 재사용
- `.report-ref`: 같은 슬라이드의 `data-report-refs` 에 포함된 정확한 리포트 anchor 링크
- `.deck-settings`, `.deck-settings-panel`, `.deck-quick-links`: 설정과 Index / Slides / Report 이동

## 리포트·슬라이드·목차 연결

- 리포트 게이트를 통과하기 전에는 슬라이드 본문을 채우지 않는다.
- 리포트의 각 핵심 섹션은 1개의 섹션 구분 슬라이드와 2\~6개의 메시지 슬라이드로 압축한다.
- 리포트 표·도형이 발표 화면에서 읽히면 같은 `src` 의 SVG를 직접 재사용한다. 복잡한 표·도형은
  의미·번호·관계를 유지하며 발표에서 읽을 부분을 재배치하고 정확한 리포트 anchor를 표시한다.
- 슬라이드의 `aria-label` 은 화면 제목보다 짧고 구체적인 목차 항목이다. `deck.js` 가 이 값을
  사용해 목차를 자동 생성한다.
- 섹션 구분 슬라이드는 목차의 시각적 경계를 만든다. `aria-label="실증 섹션"` 처럼 역할을 포함한다.
- 덱 `<main>` 에는 `data-report-source="report.html"`, 모든 `.slide` 에는 근거가 된 리포트 ID를
  `data-report-refs` 로 둔다.
- 리포트의 모든 `.report-section` 과 `data-deck-use="required"` 그림을 적어도 한 번 참조한다.

## 편집 규칙

1. 기본 HTML의 안내 문장을 실제 근거와 발표자의 해설로 모두 교체한다.
2. 각 `<section class="slide">` 에 내용을 설명하는 고유한 `aria-label` 을 둔다.
3. 각 슬라이드의 주장·표·도형이 나온 리포트 섹션·표·그림 ID를 `data-report-refs` 에 기록한다.
4. 이미지에는 구체적인 `alt` 를 적고 세미나 `assets/figs/` 아래에 저장한다.
5. 인용, 데이터와 외부 이미지는 해당 슬라이드의 `.source-note` 에 자료 이름과 확인일을 표시한다.
6. 표는 반복되는 필드를 비교할 때만 사용하고, 본문 글자 크기를 줄여 표를 욱여넣지 않는다.
7. 기본 제공 키보드 이동, 자동 목차, 진행률, 설정 패널, 테마, 전체화면 코드를 제거하지 않는다.
8. 설정 패널의 `Index / Slides / Report` 링크와 마무리 슬라이드의 링크를 유지한다.
9. 템플릿의 안내 문장, 제작 파이프라인, 슬라이드 수 운영 방식, 검토 과정 표현을 공개 산출물에
   남기지 않는다.
10. 블록 코드에는 `<pre data-code-language="Python">` 처럼 실제 언어를 지정한다.
11. 낯선 용어는 처음 등장할 때 한 문장으로 정의한다. 그림 설명은 `읽는 법 / 필요한 이유 /
    해석·실패 경계` 를 최대 세 개의 짧은 항목으로 제공한다.
12. `.code-layout` 의 좁은 우측 열에는 단일 `.panel` 만 둔다. 다열 컴포넌트를 중첩하면 각 셀이
    좁아져 한글이 어절 중간에서 깨진다.
13. 벤더 제품명·모델명·가격·한도는 바뀌므로 확인일을 함께 적는다. 확인일 없는 벤더 비교표를
    만들지 않는다.
14. 데모와 측정 결과는 실제 실행에서 관측한 것만 적는다. 재현 조건(모델·버전·환경·일자)을
    근접 출처에 남기고, 실행하지 않은 결과를 꾸며 내지 않는다.
15. 캡션은 그림의 정체성과 읽는 법을 짧게 제공한다. 긴 해석은 본문이나 다음 슬라이드로 옮기고,
    개념 모식도와 실제 측정 결과를 같은 종류의 증거처럼 보이게 하지 않는다.

## 색상 금지 규칙

이 저장소의 세미나 자료는 **사내 색을 포함할 수 없다.** 다음 토큰은 어떤 파일에도 남기지 않는다.

```text
#A50034   #6E0022
```

원자료가 사내 트랙에서 왔다면 SVG·CSS·HTML 전체에서 위 토큰을 진청 계열로 치환한 뒤 옮긴다.
`agent-support/scripts/validate-site.py` 가 이 검사를 게이트로 강제한다.

## 품질 기준

- 1280×720과 1366×768에서 제목·본문·footer가 겹치거나 잘리지 않는다.
- 프로젝터 화면에서 본문·표·근접 출처가 육안으로 읽혀야 한다.
- 390px 모바일에서 덱이 화면 안에 축소되고 버튼과 목차를 사용할 수 있다.
- 키보드 ←/→, Home/End, 목차 이동, 테마, 전체화면, 해시 URL이 동작한다.
- 모든 본문 그림은 클릭과 Enter/Space로 확대 뷰어를 열고 Esc로 닫힌다.
- 모든 블록 코드에 언어 라벨과 코드 창 헤더가 보인다.
- 설정 아이콘이 리포트와 같은 위치·형태로 보이고 `Index / Slides / Report` 가 모두 동작한다.
- 모든 일반 슬라이드에 결론형 제목과 takeaway가 있고, 근거 슬라이드에는 출처와 확인일이 있다.
- 리포트와 덱의 그림·표 번호가 각각 독립적으로 연속된다.
- 발표 자료만 읽어도 핵심 논리가 이어지며, 세부 근거는 `report.html` 에서 찾을 수 있다.
- 모든 `data-report-refs` 가 실제 리포트 ID이고, 모든 리포트 섹션과 필수 그림이 발표자료에서
  빠짐없이 다뤄진다.
- 사내 색 토큰이 0건이다.
- 인쇄/PDF에서 한 슬라이드가 한 페이지로 출력되고 제어 버튼은 숨겨진다.
